# macOS ARM64 baseline, 2026-10-26

The final focus run passed all **260 measurements**, with five samples per measurement and maximum normalized error **4.55e-15**. TN kernel source and executable suite hashes stayed unchanged during the run. This is a local performance snapshot; it establishes no machine-independent speed threshold.

Read [summary.md](summary.md) for tables with median, minimum, and maximum times. [timings.csv](timings.csv) contains every row and raw sample. [run.json](run.json) contains the shared manifest, versions, thread metadata, source hashes, cache observations, and complete backend results. Individual backend JSON, logs, and RSS reports are preserved alongside it.

## First findings

Prepared small contractions have substantial TN execution overhead even after path search and object construction are excluded. For a real chain of twelve 16-by-16 matrices, using identical input bytes and the same left-fold path:

| Implementation | Median per call |
|---|---:|
| Direct WL Dot | 8.40 us |
| TN Dot | 3.71 ms |
| TN ArrayDot | 4.23 ms |
| opt_einsum / NumPy | 86.3 us |
| cotengra / NumPy | 43.9 us |
| ITensors | 14.7 us |

The two-matrix 16-by-16 case also takes about 0.50 ms through TN Dot versus 1.26 us through direct WL Dot. Dense key generation for that case is only 10.4 us. Generic execution overhead deserves a separate profile; key generation alone cannot explain the small-case gap.

Dense plan keys grow expensive as tensor contents grow. For twelve 256-by-256 tensors, dense key generation takes 4.97 ms, versus 37.5 us for fully populated SparseArrays. The separately measured zero-mask/hash component takes 5.54 ms. These are independent noisy timings, not additive phase costs. The dense and sparse storage mechanisms differ even when support is fully populated.

All seven cache sequences give counts `[1, 1, 1, 2, 3]` for base, repeated base, changed values with the same support, changed support, and reversed output order. Numeric outputs pass throughout. The next cache investigation should preserve these semantics while examining the cost of dense support scans.

Actual ITensorMPS calls are used for MPS overlap and canonicalization. For the complex eight-site, bond-dimension-eight case, overlap takes 6.24 ms in TN and 148 us in ITensorMPS. The report labels Python's generic-network comparison and the differing canonicalization algorithms.

## Environment and replay

This run used Wolfram 15.0.1, isolated Wolfram/Arrays 1.4.2, Python 3.14.0, NumPy 2.5.4, opt_einsum 3.4.0, cotengra 0.8.3, Julia 1.12.6, ITensors 0.9.32, and ITensorMPS 0.4.2. See [python-requirements.txt](python-requirements.txt), [JuliaProject.toml](JuliaProject.toml), and [JuliaManifest.toml](JuliaManifest.toml) for dependency pins.

One thread was requested. Julia reports one BLAS thread and WL reports its configured parallel thread count. NumPy uses Accelerate, whose native version and effective thread count could not be queried here. Those values remain explicitly unknown; this is not a certified comparison of equal native BLAS thread counts. The direct WL comparison helps assess overhead within the same runtime.

The global Arrays installation was below TN's required version. An isolated source checkout of [Arrays](https://github.com/sw1sh/Arrays), commit `63cd454fb6818b5833b401b06ff231400b8c0445`, supplied version 1.4.2. No installed paclets were updated. To recreate that checkout when absent:

```sh
git clone --filter=blob:none --sparse https://github.com/sw1sh/Arrays.git Benchmarks/performance/.dependencies/Arrays
git -C Benchmarks/performance/.dependencies/Arrays sparse-checkout set Arrays
git -C Benchmarks/performance/.dependencies/Arrays checkout --detach 63cd454fb6818b5833b401b06ff231400b8c0445
```

After following the suite setup instructions, run from the repository root:

```sh
Benchmarks/performance/.venv/bin/python Benchmarks/performance/run.py \
  --profile focus \
  --arrays-directory Benchmarks/performance/.dependencies/Arrays/Arrays \
  --julia /opt/homebrew/bin/julia
```

For an exact Julia environment replay, copy this baseline's Project and Manifest into the suite's Julia environment before `Pkg.instantiate()`. The [corpus manifest](corpus-manifest.json) records every input/reference checksum. Binary corpus files are generated by the runner and are not checked in; compare checksums before interpreting a replay as identical data. Native BLAS and host load can change results.

## Verification record

Three independent review rounds reproduced the real-backend numerical run, cache behavior, API calls, timing scopes, and source guards. The last round found that Python booleans could pass as numeric measurement evidence; its original [report](verification/round3-report.md) is retained.

The final Python validator rejects booleans and nonfinite statistics/errors, and requires actual integer batch counts. The nine regression tests pass, including field-by-field malformed evidence and a complete fake-worker run. The verifier's preserved payload now fails the runner with exit code 1. A new full focus run using the corrected validator produced this baseline, and all independently measured rows also pass the corrected validator.

The final schema fix was self-tested after reaching the three-round review cap; it did not receive another independent review. The WL worker is unchanged from the last independent review. [final-validation.json](verification/final-validation.json) records the distinction and the checks performed. No TN kernel functions were modified.
